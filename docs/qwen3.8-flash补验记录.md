## 首次 Flash 实验及停止原因

初始目录：`outputs/evaluations/20261113_155355_f51fed/`。原计划三个案例各三次。前三个案例都算出 66/66 固定字段、命中最大下降渠道和品类，但均返回 partial，未完成完整报告流程：

| 案例 | 模型请求 | 工具错误 | Token | 秒 | 状态 |
|---|---:|---:|---:|---:|---|
| case_01 | 20 | 5 | 184,830 | 58.641 | partial |
| case_02 | 20 | 5 | 194,377 | 69.750 | partial |
| case_03 | 19 | 6 | 177,807 | 65.109 | partial |

问题主要是成功 SQL 会完成 task_id，但工具返回没有直接说明任务已完成与下一批可执行编号。模型把一个宽泛的下钻任务理解为可连续查询，多次复用已经完成的编号，再通过 update_plan 修复，耗尽调用或错误预算。这是工作流反馈不足，不能解释成指标计算失败，也不是模型访问失败。

确认问题重复后停止原实验：三次已经返回的 partial 保留；第四次 case_01 在请求进行中被主动终止，标记 interrupted；后五项标记 not_run，不能计作模型失败。原始协议保存在 protocol_before_abort.json，停止原因写入 protocol.json。三个已返回 partial 共记录 557,014 Token；被中断尝试的 interruption.json 记录 36,933 Token 的已知下界，在途请求总用量未知。不能把中断和未执行项当作完整九次实验。

## 最小工作流修正

没有提高模型调用预算，也没有自动生成或重新打开任务。修正包括：

- 每次工具反馈（成功或失败）都附权威的 completed、ready、blocked 状态、可执行编号、剩余预算和必做证据情况。
- 成功 SQL 明确返回 completed_task_id；新查询需要新的已登记编号。SQL 失败仍保留原编号供修复。
- 未知编号和已完成编号使用不同反馈。
- 提示模型依据当前状态选择下一步，在预算有限时优先补齐必做证据和最终报告。
- 指标结果压缩时保留 workflow，避免关键状态被上下文精简丢弃。

新增 `tests/test_workflow_feedback.py` 的五项本地测试通过，验证成功后不可复用、失败可修复、可执行任务反馈、上下文压缩以及模型确实收到成功与失败状态。测试使用本地模拟模型，不冒充真实 API 证据。

### 真实 SQL 故障恢复

目录：`outputs/recovery/20261113_161001_sql_error_3eedc4/`。首次 SQL 的实际执行文本被测试装置替换为 `SELECT injected_missing_column FROM items LIMIT 1`，数据库确实报错并返回模型。后续未注入查询成功，最终 completed，固定数值 66/66、分组来源和结构化结论检查均通过。

本次共 13 次模型请求、110,071 Token、39.219 秒。三次工具错误均保留：一次明确注入的缺字段错误、一次模型使用 SQLite 不支持的 N 前缀字符串导致语法错误，以及一次未登记图表任务编号。模型在实际反馈后修正并完成流程。注入错误不能称为模型自然生成错误；后续 SQL 语法错误则由模型实际生成。

两种恢复实验分别保存 independent_audit.json，原始轨迹、计数、源码与输入一致性均经独立核对通过。恢复用量计量完整。

最终报告需要同时呈现完成率和结论检查运行数。结论检查通过率仅以到达检查阶段的运行计算，不能用它掩盖提前 partial；结构化事实检查也不等于任意自然语言语义证明。

Flash 最终版本同时包含工作流反馈修正，与此前 27b 实验的源码不同。可以报告本次 Flash 自身的耗时与 Token 分布，但不能将不同版本之间的差异全部归因于模型切换，或将其作为严格控制变量的模型性能比较。
