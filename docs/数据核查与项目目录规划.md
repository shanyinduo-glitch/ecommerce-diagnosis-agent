## 3. 三张表的结构和粒度

### order_items.csv

每行是一条订单商品明细，并非一笔完整订单。共 9 列：

| 字段 | 含义 | 推荐读取类型及注意事项 |
|---|---|---|
| order_id | 订单编号 | 字符串，一单可有多条明细 |
| item_id | 明细编号 | 字符串，清洗键；原始数据有重复和冲突 |
| date | 原订单日期 | 显式解析日期，退款按此日期归属 |
| product_id | 商品编号 | 字符串，关联商品表 |
| channel | 渠道 | 字符串，一单只属于一个渠道 |
| quantity | 明细数量 | 正整数 |
| gross_amount | 整条明细原价金额 | 元，转为整数分或 Decimal |
| discount_amount | 整条明细优惠金额 | 元，不能再乘 quantity |
| refund_amount | 整条明细退款金额 | 元，不能再乘 quantity |

本次检查三案例的金额均为非负两位小数字符串，数量均为正整数。净销售额需要计算：gross_amount − discount_amount − refund_amount。

### products.csv

每行一个商品，共 4 列：`product_id`（唯一商品编号）、`product_name`（名称）、`category`（品类）、`list_price`（商品标价，元）。

商品标价不是订单实际成交金额。三个案例的商品表不相同，例如 P0001 标价分别为 1092.19、353.34、681.45 元。因此每个案例必须使用自己的商品表，不能把其中一张作为三案例公共维表。

### traffic.csv

每行一个日期和渠道的访客统计，共 3 列：`date`、`channel`、`visitors`。联合唯一键为 date + channel。visitors 为非负整数，跨天加总表示访客人次，不是跨天去重人数。

### 关联规则

1. 在同一案例内，订单明细通过 product_id 左关联商品表；未匹配商品保留金额、品类设为“未知”。
2. 订单明细先按 date + channel 聚合销售额与去重订单量，再与流量关联。
3. 不能把流量直接连接到每条订单明细再求和，否则访客数被放大。
4. 三案例独立运行。它们不是连续三个月、也不是训练/验证/测试切分，不能直接拼接后统一分析。
5. 编号仅在各自案例内解释。跨案例批量汇总必须带 case_id。

## 4. 实际数据质量结果

三组数据均发现：

| 检查项 | 每案例结果 | 处理要求 |
|---|---:|---|
| 完全重复的 item_id | 12 个 | 每组保留一条，共移除 12 行 |
| 字段冲突的 item_id | 4 个，涉及 8 行 | 该编号全部隔离，移除 8 行 |
| 商品关联缺失 | 8 条明细 | 保留销售金额，归入未知品类 |
| 商品主键重复 | 0 | 关联应为多对一 |
| 流量联合键重复 | 0 | 日期渠道粒度有效 |
| 同订单跨渠道或跨日期 | 0 | 当前数据符合订单约束 |
| 订单日期渠道找不到对应流量 | 0 | 当前关联覆盖完整 |

因此每案例清洗后比原始数据少 20 行。8 条未知商品明细不在删除范围。不能把这些固定数量写进算法，只用于核验公开数据。

清洗后包含多个品类的订单分别为 1446、1510、1572 笔，说明品类去重订单数不能直接相加还原总体订单数。品类金额仍具有可加性，未知品类应包含在守恒核对中。

这些检查确认了结构与指定异常，不代表已完成全部指标分析或课程评测。

## 5. 根目录内的数据安排

后续把公开数据逐文件复制到 `data/raw/public/case_01..03/`，保留现有资料包原件。复制时校验 SHA256，防止无意改动。当前尚未执行复制。

各目录职责：

- `data/raw/`：运行输入的原始版本，逻辑只读。
- `data/manifests/`：文件来源、哈希、表结构和数据版本；不放参考指标或场景答案。
- `data/generated/`：未来按其他种子生成的业务 CSV；不同数据版本单列目录。
- `evaluation/references/`：参考答案，仅评分器读取；若生成脚本同时输出答案，须与业务 CSV 分开保存。
- `outputs/runs/<case_id>/<run_id>/prepared/`：当次运行清洗数据和隔离记录，不建全局覆盖式 data/cleaned。
- `tests/fixtures/`：小型手工构造或故障注入样例，不修改公开原始数据。

Agent 每次只获准读取选定案例的三张 CSV 及当次产物。不能给它整个项目根目录访问权，因为归档资料与评测目录都可能包含答案。目录分开便于管理，实际权限隔离仍需执行工具落实。

## 7. 每次运行保存什么

```text
outputs/runs/<case_id>/<run_id>/
├── report.md
├── metrics.json
├── quality_report.json
├── prepared/                         # 清洗明细、冲突隔离记录
├── tables/                           # 总体、渠道、品类、每日、质量桥接
├── charts/                           # 至少两张图
├── code/                             # 实际执行的分析代码
├── plan_versions.jsonl
├── trace.jsonl
├── evidence_index.json
├── usage.json
├── manifest.json                     # 来源哈希、配置、版本、完成状态
└── research_handoff.json              # 可选
```

同一案例多次执行必须有不同 run_id，防止覆盖。评测结果记录被评分 run_id；故障注入实验单列，不能混作正常性能统计。后续临时文件也放在当次运行目录的临时子目录中，不向旧项目写入产物。
