# 评测方案与提交清单

正式说明要求报告关键数值正确率、主要下降来源识别率、调用次数、Token 和耗时，但未提供评分权重、误差容限和详细评分公式。以下是建议的小组评测协议，应在正式跑分前固定；教师另有规定时以教师为准。

## 数值核对

每个案例预先定义固定评分字段：整体两期净销售额、订单量、客单价、退款率、差额与变化率；各渠道和各品类两期销售额及差额；各渠道两期访客与差额；质量问题计数及清洗后行数。

- 数值正确率 = 容差内字段数 ÷ 预定字段总数，缺失或不可解析字段判错，不缩小分母。
- 金额容差建议 0.01 元；整数计数严格相等。
- 客单价与参考答案同为 4 位小数后比较；退款率与变化率按 6 位小数比较，比例与百分比先统一单位。
- 公开答案中应有而结果缺失的维度判错；额外维度应检查是否来源于数据。
- 零分母场景单独评测 null 与原因，不与普通数值混用。
- 以未展示舍入的计算值做守恒检验，报告端金额显示两位小数。

不得用参考答案直接生成报告，再声称 Agent 计算正确。评分脚本独立加载参考答案，Agent 仅访问 CSV。

## 来源识别

分开报告三个指标，避免把“最大下降分组”和“场景机制”混为一谈：

| 案例 | 最大下降渠道 | 最大下降品类 | 场景机制及目标 |
|---|---|---|---|
| case_01 | 搜索 | 家居 | 流量下降，搜索渠道 |
| case_02 | App | 数码 | 退款上升，数码品类 |
| case_03 | App | 服饰 | 客单价下降，服饰品类 |

渠道、品类识别率分别按命中案例数/3 计算。机制识别建议要求“机制+目标分组+实际指标证据”均成立，由 E/H 双人复核，并报告逐案例结果。场景标签只是生成设定；不能当成现实业务因果证明。

## 过程与性能

每次运行记录模型调用数、工具调用数、执行失败数、恢复次数、输入/输出/总 Token、端到端耗时和完成状态。模型重试也计入调用次数，失败运行也保留。API 未返回 Token 时写明缺失。

建议每个案例至少正式运行一次；预算允许时用同一配置独立运行三次，报告成功率、均值及范围，不只挑选最好的一次。记录模型、温度、提示词版本和数据哈希，确保结果可复查。

## 恢复与边界验证

| 场景 | 如何设置 | 合格表现 |
|---|---|---|
| 代码执行失败 | 在明确标记的测试运行中，让首次执行返回受控 Python 异常 | 模型读取错误，修改代码再运行，并核查修复后输出；保留原错与修正 |
| 字段缺失 | 在独立临时副本移除必要字段 | 检查缺失，说明哪些指标不能计算；可计算部分继续，不捏造字段 |
| 商品关联异常 | 使用公开数据自带无法匹配记录 | 保留销售金额，归入未知，报告数量和影响 |
| 流量键重复 | 在临时副本制造重复日期+渠道 | 检测异常，说明并采用有依据的处理或停止相关指标计算，不能任意加总 |
| 无下降 | 使用明确构造、独立标记的无下降测试数据 | 明确无下降，不生成下降贡献归因 |
| 零分母 | 构造小型边界样例 | 标记不可计算并解释原因 |
| 工具超时/达到步数上限 | 使用受控测试执行 | 正确中止，保留轨迹，明确未完成事项 |

恢复测试是单列实验，不把人为注入故障的运行混入公开案例正常性能统计。测试副本不得修改资料包原始 CSV。

## 单次分析产物

- report.md：总体变化、主要来源、指标解释、质量影响、分析局限。
- metrics.json 和关键 CSV：总体、渠道、品类、每日、访客比较。
- quality_report.json 和隔离表：重复、冲突、关联失败及处理前后影响。
- 至少两张图：每日净销售额趋势、渠道或品类销售额变化；注明时期和单位。
- trace.jsonl：简短计划、工具输入输出、报错、修改动作、结束状态。
- usage.json 与 manifest.json：成本、耗时、配置与证据索引。

## 课程总报告建议结构

1. 成员和分工：真实贡献与产物。
2. 业务目标与数据范围：销售额定义、可回答与不可回答的问题。
3. 系统实现：架构、工具、动态决策、执行反馈与恢复。
4. 数据处理和指标：口径、质量处理、拆解守恒。
5. 三案例结果：关键表图、下降来源与证据。
6. 评测：正确率、识别率、调用、Token、耗时、失败与恢复分析。
7. 反思：局限、改进方向、成本与稳定性取舍。
8. 复现说明：环境、配置、运行命令和产物位置。
